## 修复的问题

**症状**：用户在已选项目的会话里把文件拖入后说「上传归档为项目资料」「上传并归档」「归档为项目资料」，助手不处理附件，只回「还没有处理附件。你希望我先阅读分析，还是归档为项目资料？」。

**为什么必须在客户端修**：`src/member-plugin.mjs` 在**发出请求之前**就会调用 `classifyHumanIntent(text)`，一旦得到 `clarify` 便直接 `yield* clarificationStream(intent.message)` 并 `return` —— 请求根本不会到达服务端。因此服务端修好意图识别也不足以消除用户看到的现象。

**根因**：`src/human-intent.mjs` 的 `requested()` 要求归档动词紧贴子句开头。以「上传」开头的归档命令因此全部落空：

| 输入 | 修复前 | 修复后 |
| --- | --- | --- |
| 上传归档为项目资料 | clarify/missing-intent | archive |
| 上传并归档 | clarify/missing-intent | archive |
| 归档为项目资料 | clarify/missing-intent | archive |

## 修复方式

`requested()` 的归档分支新增两类表述：

1. `上传` 前缀 + 归档动词 + 真实目标（项目资料／资料库／资料／项目里／本项目／当前项目）；
2. 裸「上传并归档」「上传归档」。

客户端与服务端两份 `human-intent.mjs` 保持**逐字节一致**（客户端副本原本就与仓库内规范件同源，本次同步后经 `Compare-Object` 验证为 `IDENTICAL`）。

### 刻意保留的边界

放宽只针对归档动词，不改变安全模型：

| 输入 | 结果 | 原因 |
| --- | --- | --- |
| 上传归档为项目资料 / 上传并归档 / 归档为项目资料 | archive | 含明确归档动词与目标 |
| 归档这份文件 / 归档该文档 / 把这份资料归档到项目里 | archive | 原有规则保持 |
| 上传 / 上传这份文件 / 重新上传 | clarify | **上传单独只是传输，不构成归档授权** |
| 归档指南 / 归档说明 / 归档规则 / 归档流程 | clarify | 说明性名词是文档标题，不是命令 |
| 只阅读，不要上传并归档 | clarify | 否定词仍然生效 |
| 不要把这份文件归档，也不要上传 | clarify | 否定词仍然生效 |
| 这个应该如何归档？ / 归档是怎么回事 | clarify | 疑问句不构成指令 |

> 「上传 alone authorizes nothing」是本仓库既有的显式设计，见 `test/human-intent.test.mjs` 中 `归档、存档、上传、成果 are four different words and never interchangeable`。本次不改变它。
>
> 第一版实现曾把「归档指南」误判为归档命令，本仓库既有测试当场捕获；收紧后要求归档动词后必须跟真实目标或宾语，并禁止说明性名词。
